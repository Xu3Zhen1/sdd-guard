# sdd-guard 全面逻辑与设计意图审计

审计基线：`311a54c4055e5543e305679b4df90b4f00decf68`。日期：2026-11-13。执行环境：Windows / Node 24.19.0。

## 结论与范围

四态、流程与验收分档、外部证据、显式覆盖率的方向成立，但“绿可被信任”的设计目标尚未闭环。现有自检通过，只证明它实际执行的步骤通过；不能推出完整规格已检查、当前代码已被证据覆盖或所有跨环境行为一致。

本次对照 [README](<../README.md>)、[ICD](<ICD.md>)、[设计依据](<DESIGN-RATIONALE.md>)、[使用说明](<USAGE.md>)、[自举设计](<../changes/self-host-guard/design.md>) 与实现，分为规则、证据链、接口与集成三路审计。生产代码和既有测试保持基线，新增独立探针与本报告；下列修复项尚未实施。

证据索引：[Lead 探针](<../_work/audit-lead.mjs>)、[规则分报告](<../_work/audit-rules.md>)、[证据链分报告](<../_work/audit-evidence.md>)、[接口与自检分报告](<../_work/audit-integration.md>)。探针退出 0 表示报告所述现象被复现，其中包含故意锁定的错误 PASS，不能当作产品验收通过。

## 已证实缺口与修复验收条件

下列 A01–A16 是审计事项编号，不等同于 16 个独立缺陷：包含实测缺口、设计决策和 A12 的未测边界。P1 表示会放过本应阻断的输入、削弱实际门禁或漏掉声明的检查；P2 表示接口误导、误报、分发/文档一致性。按根因合并同类输入，避免重复计数。

### A01 · P1 · 配置有默认值表，却没有配置值域验证

位置：[配置加载](<../cli.mjs#L12>)、[嵌套判据](<../lib/rules.mjs#L694>)。

实测正常四层嵌套在阈值 3 下 FAIL；把 maxNesting 配成字符串 `garbage`，同一代码 PASS，真实 CLI exit 0，且报告打印“不得超过 garbage 层”。JSON 可解析不代表配置合法，比较时的 NaN 令全部超限条件为假。

补缺：统一验证配置对象形态、键、类型与有限数值范围；计数/窗口为合适的正整数，比例在 0..1，数组/前缀/边界形态明确。非法配置在执行前 exit 2。验收必须包含正常配置仍能拦住深嵌套，以及错误类型、负数、小数、零窗口；避免只给这一个字符串打补丁。

### A02 · P1 · 数值证据与差异统计接受不可能的计数

位置：[测试证据](<../lib/rules.mjs#L488>)、[漂移证据](<../lib/rules.mjs#L656>)、[差异计数](<../lib/rules.mjs#L760>)。

实测：tests 的 passed=-1/failed=-1 ⇒ PASS 并显示“-1 通过 / 0 失败”；passed=true/failed=null ⇒ PASS；drift 的 checks=-1/findings=-1 ⇒ PASS；diff 的 added=1000/deleted=-1000 ⇒ “0 行，均在范围内”。对应正常红样本（失败测试、正漂移、401 行超 400 预算）确实 FAIL。

补缺：所有计数使用显式非负安全整数；样本分母大于零；拒绝布尔/null/数组的隐式 Number 转换；校验总数与分项、存活 ID 唯一性及比例自洽。输入格式错误与外部证据矛盾应按统一契约分流，不能给错误 PASS。

### A03 · P1 · 仓库路径基准存在旁路

位置：[路径存在性](<../lib/rules.mjs#L1263>)、[允许前缀](<../lib/rules.mjs#L765>)。

实测：声明的 src/outside.js 在显式 repo 下不存在，只在另一个 cwd 下存在，DRY-D1 仍 PASS；允许 src/ 时，diff 路径 src/../outside.js 仍 PASS。前者验证了另一个目录的文件，后者比较了归一化之前的字符串。

补缺：显式 repo 是唯一解析基准；先规范化点段与分隔符，再判断仓库包含关系与路径段边界。明确绝对路径和仓库外路径政策，并复用同一实现到复用清单、任务、契约、diff 与边界检查。验收覆盖 cwd 同名文件、点段、前缀碰撞、根文件和合法共享路径。符号链接/大小写的全平台行为本轮未穷举。

### A04 · P1 · KISS-C1 的块计数对合法代码产生漏检

位置：[嵌套扫描](<../lib/code.mjs#L45>)。

正常多行四层控制流可被抓到；在第三层内插入对象字面量，对象的右花括号会扣减控制流深度，随后第四层最大只被计为 3；同样四层写在单行时无命中。独立探针先验证代码语法可解析，排除了语法崩溃。

补缺：每个右括号与所属的块类型配对；每行都计算实际达到的最大控制深度。对象正控、对象后深层控制流负控、单行/多行等价格式同时锁定。无 AST 是已公开边界，但不能解释已承诺“对象不计、控制流四层计”的计数错误。

### A05 · P1 · 文档格式分支弱于声明的判据

位置：[非目标列表分支](<../lib/rules.mjs#L202>)、[Markdown 分节](<../lib/md.mjs#L21>)、[单场景判据](<../lib/rules.mjs#L253>)。

三条没有任何理由的非目标 bullet PASS，而同样空理由表格 FAIL；围栏代码示例里的非目标标题也被当成正式小节；两个普通文本 THEN 不触发只识别特定行形态的多断言检查。

补缺：声明支持的 Markdown/GWT 语法，区分正文与围栏示例；所有受支持列表与表格均执行相同的必要字段检查；对不支持的格式明确拒绝或报告未检查，不返回已完整满足的结论。此处只要求结构检查一致，不要求机器判定理由是否在业务上充分。

### A06 · P1 · 自检默认漏扫入口，扫描失败没有完整性收据

位置：[默认根](<../tools/self-check.mjs#L168>)、[目录遍历](<../lib/code.mjs#L10>)。

默认根包含入口文件，但 walkCode 对根执行 readdir；文件根报错被吞后贡献零文件，最终只扫描 14 文件。--code 在接口中写的是目录，因此问题是自检自己的默认调用与接口不一致。

补缺：明确支持目录还是目录/文件，默认调用必须符合该契约；不可读、缺失、不支持与空目录分别记录。按规则报告候选文件数、已处理数、排除原因，而不只报告“规则执行了一次”。同样要防止部分子目录读取失败后扫描其余文件仍 PASS。

### A07 · P1 · 自检没有把已有重要专项与完整验收接入

位置：[测试步骤](<../tools/self-check.mjs#L66>)、[验收调用](<../tools/self-check.mjs#L186>)。

自检只登记三套基础测试；51 条专项与多根验证没有进入常规门禁。独立副本把覆盖率不足的退出从 3 改成 1，node --check 成功，自检仍 10/10；单跑 q4.5 变红。另自检既不跑 process，也不传 diff 或最低覆盖率，故验收一直允许三个 SKIP。

补缺：建立唯一测试入口并接入全部应持续守护的用例；真实 CLI 子进程断言准确的 0/1/2/3，不用“非零即正确”替代语义。自检应分别声明工具健康、自举流程和交付检查的范围。单一总覆盖率不能替代必需规则清单：即使达到 0.8，也不能允许关键 diff 规则被其他已执行规则抵消。

### A08 · P1 · 契约检查证明的是文本出现，不是执行等价

位置：[CI 等价检查](<../tools/check-contract.mjs#L242>)、[退出码比对](<../tools/check-contract.mjs#L40>)。

独立副本把发布步骤整行注释，语法通过，契约仍 53/53，实际自检变成 9/9 exit 0；因为 includes 仍能看到注释中的脚本名。把 runner 的 INCOMPLETE 改为 1，契约仍 53/53，因为比对键只列 OK/FAIL/CONFIG。

补缺：CI 与本地消费同一个结构化步骤定义，并校验执行收据、必需步骤集合及准确退出码；完整比较契约键集合与值。脚本名正则遗漏参数、shell、环境矩阵和条件，单机自检也无法等价于六环境矩阵。此前“真正等价于 CI”的结论应收窄为“同步了当前主要脚本步骤”，不能继续作为已证明的全称结论。

### A09 · P1 · 证据解析/生成器把不完整或矛盾的报告当完整证据

位置：[TAP 解析](<../lib/evidence.mjs#L12>)、[变异解析](<../lib/evidence.mjs#L47>)、[producer 退出码策略](<../tools/make-evidence.mjs#L155>)。

独立 CLI 级探针确认：同一输出先放 `tests=999/pass=999/fail=0`，后续再放真实 `tests=2/pass=1/fail=1`，parser 分字段各取首个匹配；`make-evidence` exit 0，ACCEPT-E1 也 exit 0。真实后续失败被拼成不存在的“999全绿”。

同一个 producer 入口另一个有效边界：仅输出 `M1 ✓` 一行并以 exit 1 退出，默认配置仍以该一行作为 `killed=1,total=1` 写 evidence，ACCEPT-E2 exit 0；`requireZeroExit:true` 对照则拒绝写出。exit 1 被允许有正当用途：测试生产者可以把失败用例计数交给验收规则判定；所以修复应校验摘要唯一、数量/目录完整性或为生产者设置独立严格契约，而不是机械地所有命令非零都拒收。[ICD:321](<ICD.md#L321>)仍称命令非零一律拒绝，与当前显式采信策略冲突，需同时收敛。

### A10 · P1 · 证据生产失败后旧 evidence 仍可被单独验收

位置：[只在末尾写产物](<../tools/make-evidence.mjs#L182>)、[消费预检](<../cli.mjs#L74>)。

探针先生成有效证据，再让后续测试 producer 输出无摘要文本。第二次 `make-evidence` exit 1，但旧文件字节完全不变；再将旧文件交给真实 CLI acceptance，exit 0。当前 `self-check` 会在生成前删旧 evidence，所以本情形只明确影响独立运行 make-evidence 的工作流；CLI 没有 freshness/本次 run ID 检验。

补缺：所有入口一致采取失败时不存在当前输出（原子 temp + rename，或在开始前安全隔离旧输出）；增加 run id/变更树身份并要求消费者匹配。单靠调用顺序文档不能阻止误复用。

### A11 · P2 · evidence provenance 是可选元数据，不是已校验来源

位置：[三键预检](<../cli.mjs#L74>)、[缺键实现](<../lib/evidence.mjs#L123>)、[provenance 合成](<../lib/evidence.mjs#L103>)。

手工 evidence 只含 tests/mutation/drift 三顶层键，缺少全部 meta、producer、command、cwd、exitCode、hash，真实 acceptance CLI 仍 exit 0。provenance 只是审计 metadata，不能认证生产者或抵抗恶意调用方；此处的问题是对外契约称 acceptance 消费由 producer 生成的外部证据，却没有明示/检查可信任边界。

补缺：选择一项明确产品策略：将机器判定器视为信任调用方自带证据、把本限制放入文档；或至少校验 meta schema、证据 run id 和已知生产者格式。若要抵御伪造，还需签名/可信执行身份，而不是只检查字段存在。hash 绑定到输出不等于绑定当前代码树。

同一调用还发现 `digest()` 输出 16 位十六进制前缀，却写入名为 `sha256` 的字段：这不是完整 64 位十六进制 SHA-256。对审计追溯要求“完整 SHA-256”时，应输出完整值或改清字段名与承诺。

### A12 · P2 · make-diff 的边界仍需独立行为验证

本轮未动态验证 untracked 文件、rename、binary numstat 及 staged/range 组合。代码只执行 git diff 工作树比较 [HEAD](<../tools/make-diff.mjs#L75>)；未跟踪文件通常不属于 Git diff，故新建未暂存源码可能不进入 DISCIPLINE-C1/C3。它可能是“受版本控制变更清单”的明确边界，也可能与使用者认为“本次工作树所有新增文件”不一致；目前报告不把未测推断当作实测缺陷。补缺先明确 diff 的对象范围，再给 untracked、staged、tracked-new、rename、binary 正反例。

### A13 · P2 · import 扫描把注释当成实际依赖

位置：[import 提取](<../lib/code.mjs#L140>)。

实际禁止 import FAIL、允许 import PASS；把禁止 import 放入块注释后仍 FAIL。这与已公开“不展开 tsconfig alias”不是同一个限制。补缺：至少在声明支持的语法范围内排除注释/字符串；未支持的语言或动态说明符必须显式报告。当前后缀集合有 10 种，后缀被扫描不等于所有语言的 import 和语法均受支持。

### A14 · P2 · 参数错误分流与门禁开关不够明确

位置：[参数消费](<../cli.mjs#L60>)、[覆盖率值](<../cli.mjs#L142>)。

真实 CLI 裸 --code 导致未捕获 TypeError、exit 1，而非承诺的输入错误 2；裸 --min-coverage 被 true 转换成 1；拼错 --min-covergae 不会报未知参数。后两项符合现有宽松解析形态，但会削弱“调用者显式选择”的设计依据。补缺：保留底层缺值=true 的解析兼容性时，在消费端统一验证必需值和类型；强约束运行模式拒绝未知选项，提供拼写提示。JSON 结果应包含最终 signal/coverageThreshold/coverageRatio/exitCode，并在输出前完成参数校验。

### A15 · P2 · npm 分发包含开发工具，却缺少其运行依赖

位置：[打包白名单](<../package.json#L12>)。真实 npm pack 的 29 文件包能运行 CLI help，但不含测试、自举 change 与 workflow；随包自检和契约工具退出 1。未发布 registry，也未声称核心 CLI 不可用。补缺：明确源码开发者工具边界，或打包所需依赖并做解包烟测。

### A16 · P2 · 文档漂移已存在，当前漂移检查没有拦住

[README](<../README.md#L20>)仍写“16 条机器”，档位 acceptance 写 11（实际 12），开头指向已不存在的第 3 节；CI 小节称两条同等命令、8 步且只提 Node 20/22。[CONTRIBUTING](<../CONTRIBUTING.md#L50>)也仍写 8 步。[使用说明](<USAGE.md#L212>)仍写契约 52 项，且误称自检与 CI 完全等价；[设计依据](<DESIGN-RATIONALE.md#L291>)仍写 52 项、8 步，二者还把代码后缀数写成 9（实际 10）。这些不是文字润色：会改变使用者对规则数量、检查覆盖及 CI 矩阵的理解。

更深的矛盾：[ICD](<ICD.md#L7>)自称真源，而[自举设计](<../changes/self-host-guard/design.md#L37>)称 ICD 是代码真源的人类投影；[配置契约](<../lib/contract.mjs#L80>)要求默认值变更升版本，但历史 breaking 行为仍标 0.1.0。补缺：明确规范效力层级、生成数字/覆盖所有出现点、区分历史版本与当前保证。

## 设计意图缺失的五个决策

| 需要明确的决策 | 现状 | 应补的规格 |
|---|---|---|
| 绿色究竟承诺什么 | 四态单条语义明确，聚合 exit 0 仍可伴随 SKIP/MANUAL | 定义 checked/passed/incomplete，以及交付门禁的必需规则与不适用声明 |
| 谁负责人工结案 | 6 MANUAL 恒定返回 manual；strict 只会恒红 | 人工签字的外部载体、审阅对象摘要、签字失效条件；或明确始终由外部流程承担 |
| 证据属于哪个版本 | 有命令和输出 hash，不等于代码身份 | 运行 ID、代码树/commit+dirty 摘要、配置与工具版本、原始输出引用和过期判定 |
| 流程为何算先行 | 机器读取当前四制品，无法证明写在代码之前 | 如果只查制品形态就明确命名；若承诺先规格后实现，需事件/提交链约束 |
| 对真实存量重构提供何种保证 | 名称/阈值/格式规则，无基线棘轮或语义回归覆盖 | 保持现有能力边界；把 baseline/业务回归/人工裁决列为外部集成责任，不包装成已完成的重构控制 |

跨进程本身不保证证据独立或可信；输出 hash 不保证证据对应当前代码，也不认证恶意生产者。这里优先解决误用、陈旧证据与遗漏执行，不把工具扩展为未经定义的安全系统。

## 建议实施顺序与完成判据

1. **输入与路径底座**：A01/A02/A03。先建立可复用校验与归一化，再让各规则调用，所有已复现假绿都必须变红或明确配置错误。
