# 设计说明与判据依据（DESIGN RATIONALE）

> 这份文档回答一个问题：**这套工具的每一条规则，凭什么认为自己是对的？**
>
> 它记录的不是"我们做了什么"，而是"我们否定了什么、为什么"。
> 每一条设计决策后面都跟着一次失败——没有失败支撑的决策，本文件不予收录。

**版本**：2026-11-18 · 对应 `lib/rules.mjs` 27 条规则（19 机器 + 8 人工）

---

## 0. 一句话立场

> 这个工具的目标不是"让代码符合规范"，而是**让"绿"这件事本身可信**。

推论：**假绿比假红危险**。假红会被下一次运行发现，假绿不会。

这条立场决定了后面全部设计取舍的方向。

## 1. 四态模型：为什么不是二态（Q4）

### 二态的问题

二态（pass / fail）迫使每一条判据在"没检查"时也要表态。传统做法是判 pass，
理由是"没发现问题"。**但"没检查"与"检查了没问题"症状完全相同**——两者都是"没有报错"。

### 四态的定义与分工

| 状态 | 含义 | 是否算通过 | 退出码影响 |
|---|---|---|---|
| `pass` | 机器真的执行了，且通过 | 是 | 无 |
| `fail` | 机器真的执行了，且不通过 | 否 | 1 |
| `skip` | 输入不足，**未执行** | **否** | 0（但计入覆盖率） |
| `manual` | 本质不可机械判定 | **否** | 0（`--strict` 时为 1） |

**关键不是"有四个状态"，而是"没有一个是默认通过"。**
`skip` 和 `manual` 都不计入通过，报告里单独计数并强制打印覆盖率。

### Q4 的质疑：会不会太吵，最终被人关掉？

这个质疑是对的，而且**已经在现实中发生过一次**：

> 空 change 目录 ⇒ 通过 1 · 失败 0 · 跳过 16 ⇒ **EXIT=0** ⇒ CI 放行空提交。

所以答案不是"更吵"，而是**补一个专门守这件事的开关**：`--min-coverage`。
吵的部分（`process` 档边写边查）保持不阻断；守 CI 的部分显式开启。

**为什么这不是"又一个静默跳过"**（本题最关键的分辨）：
两者区别在于**谁承担选择的责任**——使用者必须主动写 `--min-coverage 0.8` 才会生效。
而这个选择本身，又被第 2 节的"开关可察觉性"判据约束。

### 仍未解决的部分（诚实记录）

`manual` 在 `--strict` 关闭时不阻断，等于"人工签字可以永久欠着"。
目前没有机制强制它被签——这是一个已知缺口，本文件不假装解决。

## 2. 开关可关闭性分级（Q4.6）

### 原始疑问

评审者判定 `--min-coverage 0` 是**正确**的（"`0` 是显式值而非缺省"），
进而问：这个论证能不能推广？分界线在哪？

原直觉答："分界线在于关掉之后，还能不能察觉自己关掉了。"

### 把直觉变成判据

> **一个开关属于哪一档，不由"它感觉危不危险"决定，而由"关掉之后信号是否仍可分辨"决定。**
> **不可分辨 ⇒ 禁止关闭。**

| 档 | 要求 | 实例 |
|---|---|---|
| **AUDITABLE** | 关闭后留痕，且痕迹**影响机器判定** | `--min-coverage`（退 3 + 报数字）、`--skip-acceptance`（退 3） |
| **DEGRADING** | 只降级不消失：判据仍跑，结论变弱，弱化本身被记录 | `--strict`（只加强，关闭即回默认强度） |
| **FORBIDDEN** | 即使显式要求也不得关闭 | 自洽性校验（`killed+survived≠total`） |

### 为什么"只印一行文案"不合格

评审者对措辞的修正值得照录：

> **看见但无权改变仍是静默；有权选择但没告知仍是静默。两者都要成立才算显式。**

推论：如果关闭的痕迹只出现在 stdout 而退出码仍是 0，CI 与自动化调用方都读不到它。
**痕迹必须进机器可读的那一层。**

### 据此修掉的真实缺陷

`--skip-acceptance` 原先无条件 `exit 0`，只在文案里加一句"本次不构成交付验收"：

```
$ node tools/self-check.mjs --skip-acceptance
全部 7/8 项通过（验收已跳过，本次不构成交付验收）
EXIT=0          ← 跳过了验收，与验收通过不可区分
```

改为退 **3**。登记表在 `lib/contract.mjs` 的 `SWITCHES`，
`tools/check-contract.mjs` 强制校验：新增布尔开关未登记即报漂移；
FORBIDDEN 档若出现在 `--help` 里也报漂移。

## 3. 两种失败信号必须分开（Q4.5）

### 问题

原先两种**语义相反**的失败共用退出码 1：

| 信号 | 含义 | 排障方向 |
|---|---|---|
| 「我没跑完」 | 覆盖率不足 | 指向**输入**（补文档） |
| 「跑完但不可信」 | 判据自相矛盾/内部崩溃 | 指向**判据本身** |

CI 只能写 `if exit != 0`，于是要么把"需要补文档"当成"代码有问题"，
要么把"判据自相矛盾"当普通不合格放过去——**后者是假绿**。

### 现在的退出码语义

| 码 | 含义 | 对谁下结论 |
|---|---|---|
| `0` | 全过 | — |
| `1` | 判据判定不合格 | 对**被测对象** |
| `2` | 输入/配置错误 | 根本没开始跑 |
| `3` | 判据自身不可信 / 没跑完 | 对**判据自身** |

**优先级 `3 > 1`**：判据自己都不可信时，它报的 `fail` 也不该当作对被测对象的结论。
规则 `run()` 抛异常时标记 `signal:"untrusted"`，走 3 而非 1。

### 2026-11-18 补：三种"没跑完"要分开算（外部实测 ④）

同一张表里其实有三种不同的"没跑完"，混在一起就会各自漏一角：

| 形状 | 例子 | 正确的码 | 由谁负责 |
|---|---|---|---|
| 选中了机器规则，但**输入不足** | 空 change 目录 ⇒ `covered=1/17` | 0（默认） | `--min-coverage`（显式选择） |
| **一条机器规则都没选中** | `--only KISS-C2`（唯一 MANUAL）⇒ `0/0` | **3** | 规则本身（2026-11-18 修） |
| 判据**自身不可信** | `run()` 抛异常 / 证据自相矛盾 | 3（signal=untrusted） | 规则本身的信号 |

第二行原先退 **0**：8 条 MANUAL 规则逐条实测全部 `0/0 ⇒ exit 0`，CI 会把"一条机器规则都没跑"读成"全过"。

**为什么不是 1 或 2**：不是 1（没有任何机器判据说"你不合格"）；不是 2（`--only <manual id>` 是打印人工清单的合法用法）。
**为什么不能把第一行也一起判 3**：那样 `process` 档"边写边查"的初稿阶段会被自己的门禁打断 —— 这正是当初 `--min-coverage` 默认关闭的理由。
**判据**：空集要分"没选中"与"选中了但没跑"两种；只把前者能确定的那个判死，后者交给显式阈值。
本条的回归测试同时钉住两边：正控（`machineTotal=0 ⇒ 3`）与**反向**（`machineTotal=1, covered=0 ⇒ 仍 0`）；
变异负控：把条件放宽成 `covered===0` ⇒ 反向用例变红；把 3 改成 1 ⇒ 正控变红。

## 4. 「不可达分支」的正确处理（Q3）

### 问题

`killed > effectiveTotal` 经穷举 454 组证实不可达（可达 0）。
原实现写成 `if (...) return {status:"fail"}` —— **永不执行**。

**永不执行的代码与"根本不存在"在可观测行为上完全等价**：测不到它，
也没人能证明它还能工作（万一有人改坏上游条件？）。这是"变相的未测试分支"。

### 解法：不删，但改变存在方式

| 存在方式 | 行为 |
|---|---|
| `if (...) return fail` | 不满足条件才执行 ⇒ 永真 ⇒ **死代码** |
| `assertInvariant(...)` | 每次运行都求值并记账 ⇒ **活的检查点** |

不变量被破坏时抛错，走第 3 节的 `untrusted` 通道得到退出码 3。

**为什么不删**：删掉它需要"上游一定不出错"这个假设，而该假设依赖自洽性校验、
豁免去重、`survivedIds` 对齐三处同时正确。**判据越复杂，假设越不可靠。**
一旦破了，后果是静默输出 `rate > 1` 并判 PASS。

测试的关键不在"没抛错"，而在断言 `calls > 0` ——**「没抛错」与「没调用」症状同形**。

## 5. 判据之间的职责重叠（Q2）

### 疑问

`DISCIPLINE-C1`（变更落在声明范围 + 行数预算）和 `DISCIPLINE-C3`（文档↔代码绑定）
都在管"声明 vs 实际"。C3 的反向检查是否已经弱到没有价值？

### 实测回答（不看代码，只看行为）

| # | 场景 | 结论 |
|---|---|---|
| P0 | 文档完全没提（正控） | **FAIL** ✅ |
| S1 | 文档写「本次不修改 ghost.js」 | pass（假阴性） |
| S2 | 「上一版本的 ghost.js…」 | pass（假阴性） |
| S3 | 只提 stem 且长度 <8 | **FAIL** ✅ |
| S4 | specs 里正常披露 | pass（**修复前 FAIL**） |
| S5 | 另一个目录下的同名文件 | pass（假阴性） |
| S6 | tools/ 下未披露 | **FAIL** ✅ |

### 结论

**弱检查有价值，但价值点在"兜底"不在"覆盖"。**

它现在的能力是：只要有人在新文件的名字上完全不留痕，就会被抓。
它做不到的：判断文档里那句话是不是在说这个文件——而这恰恰是"是否真的披露"所需要的。

真阳性 3 个、假阴性 3 个。判据是无上下文的子串匹配，**注定分不清「我要改它」和「我不改它」**。

### 实测抓到的两个真问题

**① C3 根本没读 specs**：`listArtifacts` 把 specs 放在 `art.specs` 数组，
而 `allArtText` 只遍历 `ctx.art.files`（proposal/design/tasks）。
**而代码注释写的是「文档全文（含 specs）」——注释比实现更宽。**
在 `specs/spec.md` 里正常披露的文件会被判"改了但文档没提"。方向安全（假红），
但噪音的结局通常是被整条关掉。

**② pass 文案在骗人**：旧文案「N 个变更文件均可在文档中找到出处」暗示文档确实说了这件事，
而实现只证明"文件名作为子串出现过"。改为「仅名称匹配，不判断上下文」。

**没有加强判据本身**：加强它需要语义理解；强行加强只会重演第 6 节的六个后门循环
（为了消误报而加豁免 ⇒ 造出新的绕过面）。**弱检查就该老实承认自己弱。**

### 2026-11-18 附：「体为空」到底指什么（ARCH-07 统一口径）

同一个词在两处用了两套标准，是这次外部实测翻出来的：

| 形态 | 旧判定 | 为什么错 |
|---|---|---|
| `catch {}` | 空 | — |
| `catch { /* ignore */ }` | 空 | ✓ 对的 |
| `catch {\n // ignore\n}` | 空 | ✓ 对的 |
| `catch { ; }` | **非空** | ✗ `;` 是空语句，什么也不做 |

**判据**：**去掉注释与空语句后是否还剩东西**。一条式子，三种形态同解。
`;` 旧被判非空，纯粹因为判据写成了 `bare.trim() !== ''` —— **拿"有没有字符"冒充"有没有语句"**。

**但措辞必须分档**（这是另一半）：

- `catch {}` ⇒ 「体为空，异常被完全吞掉」
- `catch { /* … */ }` ⇒ 「体为空（**仅有注释，注释不处理异常**）」

理由：实测本仓库 6 处空 catch 里 **5 处写了注释**。一律说"完全吞掉"，读者会以为连说明都没有 ——
**报告让事实失真，与判据判错是同族的两种失真**。

**明确否定的放宽**：不把"有注释"判为通过。那会开出一条**不需要登记、不需要 `reason`、
还能绕过 `catchAllowlist` 审计**的豁免通道 —— 写一行 `// ignore` 就过。注释是给人看的，
不是给运行时看的；它不消费异常、不记录、不降级、不重抛。
这与「主张不能替代行为」是同一条原则，也是本项目拒绝为它开配置项的理由。

### 2026-11-18 附：DRY-T1 的"没写路径"与"没写反引号"（外部实测 ③）

抽取键原是「反引号包裹」。后果：`- [ ] alpha6/some.js` 被判「未给出任何具体文件路径」——
**把"没写反引号"读成"没写路径"**。方向是 fail-closed（不会放过幽灵路径），但读者会被误导。

**为什么不直接用"含 `/` 的裸 token"**（实测否决）：

| 候选 | 真实身份 |
|---|---|
| `12/12` `4/4` `6/6` | 进度分数 |
| `ACCEPT-E1/E3` `A04/A06/A13` | 规则 id 组合 |
| `只计控制流/函数体块` | 叙述文字 |

本仓库两个真实 `tasks.md` 的裸候选 **8 个，8 个全是误报**。只靠"有分隔符"判，精确率为 0。

**采用的判据**：裸路径**必须带源码类扩展名**（`SOURCE_EXT_RE`）。
加上这道门槛后，同一批文件裸候选 **0 条**（真阳性 0 / 误报 0），而正控夹具 `alpha6/some.js` 命中。
两条通道因此分工明确：

- **反引号通道**：含分隔符即算，**不限扩展名**（`src/export/extless/index` 有效）
- **裸路径通道**：**必须带扩展名**；无扩展名的裸路径抽不到 —— 这是**已知分界**，补写法是用反引号

**判据**：放宽抽取面时，"放宽到什么程度"必须由**反例集合**决定，不能由直觉决定。
这里反例是 8 条实测误报；没有它们，`/[\/]/` 这种判法看起来完全合理。

### 2026-11-19 复核补：放宽**放在哪一层**比放宽多少更要紧

第一版我把裸通道写进了共用的 `extractPaths`，理由是「只增加候选 ⇒ 只会更严」。
**这个推理是错的**，因为它默认了所有调用方的判定都是单调的。实测不成立：

| 调用方 | 候选为空的语义 | 加候选的后果 |
|---|---|---|
| `DRY-T1` | FAIL（一条路径都没给） | 每条都要 `existsProjectFile` ⇒ **更严** ✓ |
| `DRY-D1` | FAIL（复用清单仅 0 条，需 ≥ 1） | 0→1 ⇒ **FAIL 洗成 PASS** ✗ |
| `DECOUPLE-1` | FAIL（没有给出任何具体文件路径） | 0→1 ⇒ **FAIL 洗成 PASS** ✗ |
| `DISCIPLINE-C3` | 抽到的路径进 `declared`（"文档声明过"） | 候选变多 ⇒ 更容易满足 ⇒ **放松** ✗ |

实测翻转（父提交 worktree 对照）：
「- 先看看 `tools/make-diff.mjs` 是怎么写的」原本报"复用清单仅 0 条路径"，加裸通道后 **PASS** ——
而这句话的字面意思是"我看看它怎么写"，**不是"我要复用它的能力"**。
第二例更糟：「参考 `lib/contract.mjs` 的写法就行，**本次不动它**」被判成"本次的契约单一真源"。

**为什么本仓看不到**：本仓 `design.md` 本来就写了反引号路径（DRY-D1 5 条、DECOUPLE-1 2 条），
非空且全部存在 —— **恰好是唯一没有洞的那个分支**。
用一个仓库的通过样本去证明跨规则安全，正是这套工具反对的"没检查 ≠ 检查通过"。

**判据**：**放宽要落在"消费方"，不是"生产方"**。
共用原语（抽取器）只回答"文本里有哪些像路径的串"；**"这些串算不算声明/复用/契约"是各规则的判断**，
不能由抽取器替它们决定。修法：`extractPaths(text, { bare: false })` 默认关，只有 DRY-T1 开。

### 2026-11-19 补：DRY-C1 的 OOM 不是"内存不够"，是"把全部命中物化了"

**实测（本机，`G:/AMup`，`--only DRY-C1`）**：

| 堆上限 | 结果 |
|---|---|
| 默认 4,288 MB | 28.6 s，**exit 134**，输出 0 字节 |
| 8 GB | 44.7 s，仍 exit 134 |
| 12 GB | 68.6 s，仍 exit 134 |

**给多大堆就在多大处崩**——这不是"堆小了"，是需求不收敛。

**钱花在哪（`--expose-gc` 实测 800 文件样本）**：≈631 B/窗口 =
key 文本 324 B ＋ **sample 摘要 165 B（只用于报告）** ＋ Map 桶与对象 142 B。
乘 1,566 万窗口 ≈ 9.2 GB。

**真正的大头不是索引，是命中数**：该语料跨文件命中 **1,292 万条**，旧实现把它们**全部 push 进 `found` 数组**，再排序、分组。
1292 万个对象（每个含 a/b 两个坐标对象 + sample 字符串）就是这个量级的来源。

**修法（判定语义一行不改）**：分组键 =（文件对, a 侧文件, 行差），它**已经唯一确定 b 侧文件**；
而文件顺序扫、窗口行递增 ⇒ **同组命中天然按 a.line 递增到达**。
于是"先收齐 1292 万条再排序分组"是多余的：边扫边合并、每个文件扫完收尾即可。
索引里也只剩 `{line, file}`（key 就是 Map 的键），`sample` 只在**命中**时才拼。

### 2026-11-20 补：裸路径通道的外部反例集（glob 不是文件）

**债务**：裸路径通道（③）此前只有本仓两份 `tasks.md` 作证据 —— 裸候选 0 条，证明不了外部仓不误报。

**补测（`G:/AMup` 真实文档，非构造）**：

| 语料 | 规模 | 裸候选 | 噪声 |
|---|---|---|---|
| 全部 `.md` | 12,757 份 | 22,360 条 | **1,019 条含 `* ? { }`** |
| `tasks.md`（去重后） | 11 份 | 1 条 | **0** |

**发现的真缺陷**：像 `specs/*.md` 这种 glob 通配、以及 `requiresApproval\s*[:=]` 这种正则片段，
会被「含分隔符 ＋ 源码扩展名」两条门槛收进来，再被 DRY-T1 判成「不存在且未标注新建」⇒ **假红**。
文件系统里 `*` `?` `{` `}` 本无意义，它们不可能是「任务要改的文件」。

**修法**：裸通道里加一条 `if (/[*?{}]/.test(t)) continue;`。
**为什么不连方括号一起拒**：Next.js 的 `app/[...slug]/page.tsx` 是**真路径**，
方括号在真实文件名里合法 —— 误伤它的代价高于放过个别 JSON 路径（实测残余仅 1 条）。

**集合差证明（不是「看起来少了」）**：修前裸候选 22,360 → 修后 **21,341**，差额 **1,019** 恰好等于含 `*?{}` 的条数；
修后 `stillHasMeta = 0`，**其余候选一条未动**。

**外部真例（假红 → 正确绿）**：`G:/AMup/upstream-v4/openspec/changes/three-light-skins/tasks.md` 原文写作
`Final evidence: docs/skin-figures/iter5-final/README.md.`（叙述句里的裸路径，无反引号）：

| 版本 | DRY-T1 结论 |
|---|---|
| `2c1064b~1`（裸通道之前） | **FAIL**「tasks.md 未给出任何具体文件路径」 |
| `2c1064b` 起（含本次修复） | **PASS**「1 条路径均可定位或已标注新建」 |

**判据（可复用）**：**「反例集」要能同时证两件事** —— 该拒的拒掉（召回没被放宽），
该留的留下（精确率没被误伤）。只报「噪声清零」而不给「其余候选一条未动」，等于把判据改松了还不知道。

**判据（可复用）**：**当"输出"本身是 O(命中数) 时，先问"这些命中是否已经天然有序"** ——
若已经有序，"收集 + 排序"两步都可以删掉，内存从 O(全部命中) 降到 O(当前未收尾的段数)。

**语义不变的证据（不是"看起来一样"）**：把改前/改后两个实现并排跑，
在本仓（83 段 / 窗口 6）、AMup 前 400 文件（8,715 段）、AMup 重复密集段（405 段）、
以及 **AMup 前 5,000 文件（126,760 段）** 上逐字段比对 `{size,a,b,span,windows,sample}`：**完全相同**；
窗口 3 也跑了同样的对照。

### 2026-11-19 第二刀：连"段数组"本身也不留

第一刀之后仍在 1 GB 堆上崩。再量一次就清楚了：**输出本身**是 1,643,535 段 × 679 B ≈ **1,064 MB** 常驻
（其中 `sample` 摘要 376 MB），消费端再 `map` 成 entries 又 **380 MB**。

而 DRY-C1 真正需要的只有两样：**总数** 和 **每文件至多 30 条样例**（`items` 上限就是 30 条）。
164 万段里它一条都不留。

**两条改动**（都不动判定语义）：

1. `createRunMerger(size, onRun)` —— 给了回调就**逐段交付、不入数组**；没给回调行为不变（测试依赖完整数组）。
2. DRY-C1 改用回调，自己维护「每个 a 侧文件的命中计数 + 至多 30 条样例」。
   `aggregateByFile` 增加"真实总数"入参：**样例可能被截断，但计数必须是真值** ——
   否则报告里的"N 处"会变成"样例条数"，那是同一族的假数字。

**实测（`G:/AMup` 全量，`--only DRY-C1`）**：

| 堆上限 | 第一刀 | 第二刀 |
|---|---|---|
| 4,288 MB（默认） | 48.9 s · exit 1 | 43 s 量级 · exit 1 |
| 1,024 MB | exit 134 | **45.0 s · exit 1 · 10,521 字节** |
| **768 MB** | exit 134 | **43.6 s · exit 1 · 10,521 字节** |

**判据（可复用）**：**先问"消费方到底需要哪几样"，再决定"生产方要不要把全部产出留在内存里"。**
这里生产方每段都留，而消费方只需要"总数 + 前 30 条" —— **1.4 GB 里 99.99% 是白留的**。

## 6. 最危险的一类缺陷：为消除误报而扩大的"跳过面"

九轮对抗性实测中，最反复出现的模式是：

> 因为某条判据误报了 → 加一个豁免词 / 扩大跳过条件 → 误报消失，**真实问题也一起消失**。

| # | 位置 | 后门形态 |
|---|---|---|
| R1 | `NOT_CHANGING` | 整块包含匹配，无修饰范围判断：「修改 X（日志格式不适用）」被整条跳过 |
| R2 | `RECON_HEAD` | 句首写「确认」即脱离"必须被改"管辖 |
| R3 | `looksLikePath` | 含 `--` 一律不当路径 + 要求扩展名 ⇒ 幽灵文件与无扩展名文件全免检 |
| R4 | `splitCommandPaths` | 无引号感知，含空格路径被切碎后三通道全哑 |
| R5 | `toBlocks` | 续行只认 ≥2 空格，单 Tab 整行被丢弃 |
| R6 | `codeScopes` | 默认白名单只含 `lib/ src/ app/ packages/`，`tools/ scripts/ bin/` 整段免检 |

### 修复方向的一致原则

**收紧，而不是跳过**。具体到 R1 的修正最能说明问题：

早先的修法是把被豁免的路径降级为"只查存在性"——但注入用例的形态是
「修改 `src/util/text.js` 的归一化（日志格式不适用本次封装）」，
这里的"不适用"修饰的是**日志格式**，而这个文件**确实要改**。
降级为存在性检查后，文件真实存在 ⇒ PASS ⇒ 真问题照样被吞。

**正确语义：豁免词只影响人类阅读，不影响判据。** 路径一律进 `declared`。

### 2026-11-18 补：扫描面的跳过也必须留痕（外部实测）

前面的 R1–R6 都在"规则内部"扩大跳过面；**文件根本进不了扫描**是同一族的更坏形态 ——
连"这条规则看过它"都无从谈起。

**实证**（`g:/AMup`，27,075 个 JS，无 git、多副本）：`vendor` 被 `SKIP_DIRS` 整目录跳过，
937 个源码文件既不进 `candidates`，也不进 `errors` / `excluded`。
27075 − 937 = 26138，与 ARCH-06 自报的"实检"数字**逐字相等** —— 数字对得上，但收据里没有任何痕迹。

**判据（三条同时成立才算留痕）**：

1. **可归因**：每条跳过要有 `{path, reason, files}`，`reason` 至少区分
   `builtin`（内置黑名单）/ `caller`（调用方点名）/ `dot-dir`（一级点目录）。
   只报一个总数回答不了"哪 937 个、为什么"。
2. **可复算**：`count === Σ dirs[].files`，且**嵌套不重计**（vendor 里再有 node_modules 只算外层）。
3. **不变量**：`candidates + blacklisted.count` = 该扫描面上按后缀物理存在的源码文件数。
   这是唯一能证明"没有别的静默出口"的算式。

**两个已否定的简化**：

- 「黑名单是用户自己的选择，不必报」—— 用户选的是"不扫这个目录"，不是"不告诉我跳过了多少"。
  与 gitignore 的 `reason` + `sample` 相比，**收据结构不对称**本身就是缺陷信号。
- 「只把 `count` 加进收据就够」—— 没有逐目录 `files` 时 `count` 无法被第三方复算，
  退化成"看着像数据、其实是没测"的假字段（本项目在 t-gates 抓过一次同形态）。

## 7. 这套方法可迁移吗（Q5）

### 五条元判据

1. 写绕过负控**之前**先写豁免
2. 收紧修的是假阳性，跳过造成的是假阴性
3. 跳过必须显式
4. 跳过是分层的——整篇级跳过会让规则以为自己无事可做
5. 退出码要回答"我跑完了吗"，而不只是"我判断错了吗"

### Q5 的猜测与回应

评审者猜"第 3 条（跳过必须显式）在其他领域会最先失效，因为业务上的跳过理由更多"。

**这个猜测部分成立，但失效方式与直觉相反。**

不是因为"业务理由多"——理由多恰恰更需要显式。真正先失效的是**第 4 条（跳过是分层的）**：

sdd-guard 处理的是**单一文档集合**，"整篇级跳过"只有一种（反引号未闭合）。
而迁移到 API 契约检查、数据质量校验时，被测对象是**分片**的
（每个 endpoint / 每张表 / 每个批次各自独立），于是：

> "这一条我跳过了" 与 "整个校验我跳过了" 会在同一个报告里混在一起，
> 而使用者默认读到的结论是后者。

**判据**：迁移到任何**分片对象**的领域时，必须先在报告结构上把
"条目级跳过"与"整体级跳过"分成两栏计数，否则第 4 条元判据会在无声中失效。

### 已经用真实证据验证过的迁移点

`--min-coverage` 的引入本身就是一次微型的跨领域迁移：
从"单条规则的四态"迁移到"整体覆盖率的四态"，立刻暴露出
"空集不构成通过"这条判据在**聚合层**同样适用（空 change 目录 ⇒ EXIT=0）。
