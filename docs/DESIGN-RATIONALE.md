# 设计说明与判据依据（DESIGN RATIONALE）

> 这份文档回答一个问题：**这套工具的每一条规则，凭什么认为自己是对的？**
>
> 它记录的不是"我们做了什么"，而是"我们否定了什么、为什么"。
> 每一条设计决策后面都跟着一次失败——没有失败支撑的决策，本文件不予收录。

**版本**：2026-11-13 · 对应 `lib/rules.mjs` 23 条规则（17 机器 + 6 人工）

---

## 0. 一句话立场

> 这个工具的目标不是"让代码符合规范"，而是**让"绿"这件事本身可信**。

推论：**假绿比假红危险**。假红会被下一次运行发现，假绿不会。

这条立场决定了后面全部设计取舍的方向。

## 1. 四态模型：为什么不是二态（Q4）

### 二态的问题

二态（pass / fail）迫使每一条判据在"没检查"时也要表态。传统做法是判 pass，
理由是"没发现问题"。**但"没检查"与"检查了没问题"症状完全相同**——两者都是"没有报错"。

### 四态的定义与分工

| 状态 | 含义 | 是否算通过 | 退出码影响 |
|---|---|---|---|
| `pass` | 机器真的执行了，且通过 | 是 | 无 |
| `fail` | 机器真的执行了，且不通过 | 否 | 1 |
| `skip` | 输入不足，**未执行** | **否** | 0（但计入覆盖率） |
| `manual` | 本质不可机械判定 | **否** | 0（`--strict` 时为 1） |

**关键不是"有四个状态"，而是"没有一个是默认通过"。**
`skip` 和 `manual` 都不计入通过，报告里单独计数并强制打印覆盖率。

### Q4 的质疑：会不会太吵，最终被人关掉？

这个质疑是对的，而且**已经在现实中发生过一次**：

> 空 change 目录 ⇒ 通过 1 · 失败 0 · 跳过 16 ⇒ **EXIT=0** ⇒ CI 放行空提交。

所以答案不是"更吵"，而是**补一个专门守这件事的开关**：`--min-coverage`。
吵的部分（`process` 档边写边查）保持不阻断；守 CI 的部分显式开启。

**为什么这不是"又一个静默跳过"**（本题最关键的分辨）：
两者区别在于**谁承担选择的责任**——使用者必须主动写 `--min-coverage 0.8` 才会生效。
而这个选择本身，又被第 2 节的"开关可察觉性"判据约束。

### 仍未解决的部分（诚实记录）

`manual` 在 `--strict` 关闭时不阻断，等于"人工签字可以永久欠着"。
目前没有机制强制它被签——这是一个已知缺口，本文件不假装解决。

## 2. 开关可关闭性分级（Q4.6）

### 原始疑问

评审者判定 `--min-coverage 0` 是**正确**的（"`0` 是显式值而非缺省"），
进而问：这个论证能不能推广？分界线在哪？

原直觉答："分界线在于关掉之后，还能不能察觉自己关掉了。"

### 把直觉变成判据

> **一个开关属于哪一档，不由"它感觉危不危险"决定，而由"关掉之后信号是否仍可分辨"决定。**
> **不可分辨 ⇒ 禁止关闭。**

| 档 | 要求 | 实例 |
|---|---|---|
| **AUDITABLE** | 关闭后留痕，且痕迹**影响机器判定** | `--min-coverage`（退 3 + 报数字）、`--skip-acceptance`（退 3） |
| **DEGRADING** | 只降级不消失：判据仍跑，结论变弱，弱化本身被记录 | `--strict`（只加强，关闭即回默认强度） |
| **FORBIDDEN** | 即使显式要求也不得关闭 | 自洽性校验（`killed+survived≠total`） |

### 为什么"只印一行文案"不合格

评审者对措辞的修正值得照录：

> **看见但无权改变仍是静默；有权选择但没告知仍是静默。两者都要成立才算显式。**

推论：如果关闭的痕迹只出现在 stdout 而退出码仍是 0，CI 与自动化调用方都读不到它。
**痕迹必须进机器可读的那一层。**

### 据此修掉的真实缺陷

`--skip-acceptance` 原先无条件 `exit 0`，只在文案里加一句"本次不构成交付验收"：

```
$ node tools/self-check.mjs --skip-acceptance
全部 7/8 项通过（验收已跳过，本次不构成交付验收）
EXIT=0          ← 跳过了验收，与验收通过不可区分
```

改为退 **3**。登记表在 `lib/contract.mjs` 的 `SWITCHES`，
`tools/check-contract.mjs` 强制校验：新增布尔开关未登记即报漂移；
FORBIDDEN 档若出现在 `--help` 里也报漂移。

## 3. 两种失败信号必须分开（Q4.5）

### 问题

原先两种**语义相反**的失败共用退出码 1：

| 信号 | 含义 | 排障方向 |
|---|---|---|
| 「我没跑完」 | 覆盖率不足 | 指向**输入**（补文档） |
| 「跑完但不可信」 | 判据自相矛盾/内部崩溃 | 指向**判据本身** |

CI 只能写 `if exit != 0`，于是要么把"需要补文档"当成"代码有问题"，
要么把"判据自相矛盾"当普通不合格放过去——**后者是假绿**。

### 现在的退出码语义

| 码 | 含义 | 对谁下结论 |
|---|---|---|
| `0` | 全过 | — |
| `1` | 判据判定不合格 | 对**被测对象** |
| `2` | 输入/配置错误 | 根本没开始跑 |
| `3` | 判据自身不可信 / 没跑完 | 对**判据自身** |

**优先级 `3 > 1`**：判据自己都不可信时，它报的 `fail` 也不该当作对被测对象的结论。
规则 `run()` 抛异常时标记 `signal:"untrusted"`，走 3 而非 1。

## 4. 「不可达分支」的正确处理（Q3）

### 问题

`killed > effectiveTotal` 经穷举 454 组证实不可达（可达 0）。
原实现写成 `if (...) return {status:"fail"}` —— **永不执行**。

**永不执行的代码与"根本不存在"在可观测行为上完全等价**：测不到它，
也没人能证明它还能工作（万一有人改坏上游条件？）。这是"变相的未测试分支"。

### 解法：不删，但改变存在方式

| 存在方式 | 行为 |
|---|---|
| `if (...) return fail` | 不满足条件才执行 ⇒ 永真 ⇒ **死代码** |
| `assertInvariant(...)` | 每次运行都求值并记账 ⇒ **活的检查点** |

不变量被破坏时抛错，走第 3 节的 `untrusted` 通道得到退出码 3。

**为什么不删**：删掉它需要"上游一定不出错"这个假设，而该假设依赖自洽性校验、
豁免去重、`survivedIds` 对齐三处同时正确。**判据越复杂，假设越不可靠。**
一旦破了，后果是静默输出 `rate > 1` 并判 PASS。

测试的关键不在"没抛错"，而在断言 `calls > 0` ——**「没抛错」与「没调用」症状同形**。

## 5. 判据之间的职责重叠（Q2）

### 疑问

`DISCIPLINE-C1`（变更落在声明范围 + 行数预算）和 `DISCIPLINE-C3`（文档↔代码绑定）
都在管"声明 vs 实际"。C3 的反向检查是否已经弱到没有价值？

### 实测回答（不看代码，只看行为）

| # | 场景 | 结论 |
|---|---|---|
| P0 | 文档完全没提（正控） | **FAIL** ✅ |
| S1 | 文档写「本次不修改 ghost.js」 | pass（假阴性） |
| S2 | 「上一版本的 ghost.js…」 | pass（假阴性） |
| S3 | 只提 stem 且长度 <8 | **FAIL** ✅ |
| S4 | specs 里正常披露 | pass（**修复前 FAIL**） |
| S5 | 另一个目录下的同名文件 | pass（假阴性） |
| S6 | tools/ 下未披露 | **FAIL** ✅ |

### 结论

**弱检查有价值，但价值点在"兜底"不在"覆盖"。**

它现在的能力是：只要有人在新文件的名字上完全不留痕，就会被抓。
它做不到的：判断文档里那句话是不是在说这个文件——而这恰恰是"是否真的披露"所需要的。

真阳性 3 个、假阴性 3 个。判据是无上下文的子串匹配，**注定分不清「我要改它」和「我不改它」**。

### 实测抓到的两个真问题

**① C3 根本没读 specs**：`listArtifacts` 把 specs 放在 `art.specs` 数组，
而 `allArtText` 只遍历 `ctx.art.files`（proposal/design/tasks）。
**而代码注释写的是「文档全文（含 specs）」——注释比实现更宽。**
在 `specs/spec.md` 里正常披露的文件会被判"改了但文档没提"。方向安全（假红），
但噪音的结局通常是被整条关掉。

**② pass 文案在骗人**：旧文案「N 个变更文件均可在文档中找到出处」暗示文档确实说了这件事，
而实现只证明"文件名作为子串出现过"。改为「仅名称匹配，不判断上下文」。

**没有加强判据本身**：加强它需要语义理解；强行加强只会重演第 6 节的六个后门循环
（为了消误报而加豁免 ⇒ 造出新的绕过面）。**弱检查就该老实承认自己弱。**

## 6. 最危险的一类缺陷：为消除误报而扩大的"跳过面"

九轮对抗性实测中，最反复出现的模式是：

> 因为某条判据误报了 → 加一个豁免词 / 扩大跳过条件 → 误报消失，**真实问题也一起消失**。

| # | 位置 | 后门形态 |
|---|---|---|
| R1 | `NOT_CHANGING` | 整块包含匹配，无修饰范围判断：「修改 X（日志格式不适用）」被整条跳过 |
| R2 | `RECON_HEAD` | 句首写「确认」即脱离"必须被改"管辖 |
| R3 | `looksLikePath` | 含 `--` 一律不当路径 + 要求扩展名 ⇒ 幽灵文件与无扩展名文件全免检 |
| R4 | `splitCommandPaths` | 无引号感知，含空格路径被切碎后三通道全哑 |
| R5 | `toBlocks` | 续行只认 ≥2 空格，单 Tab 整行被丢弃 |
| R6 | `codeScopes` | 默认白名单只含 `lib/ src/ app/ packages/`，`tools/ scripts/ bin/` 整段免检 |

### 修复方向的一致原则

**收紧，而不是跳过**。具体到 R1 的修正最能说明问题：

早先的修法是把被豁免的路径降级为"只查存在性"——但注入用例的形态是
「修改 `src/util/text.js` 的归一化（日志格式不适用本次封装）」，
这里的"不适用"修饰的是**日志格式**，而这个文件**确实要改**。
降级为存在性检查后，文件真实存在 ⇒ PASS ⇒ 真问题照样被吞。

**正确语义：豁免词只影响人类阅读，不影响判据。** 路径一律进 `declared`。

## 7. 这套方法可迁移吗（Q5）

### 五条元判据

1. 写绕过负控**之前**先写豁免
2. 收紧修的是假阳性，跳过造成的是假阴性
3. 跳过必须显式
4. 跳过是分层的——整篇级跳过会让规则以为自己无事可做
5. 退出码要回答"我跑完了吗"，而不只是"我判断错了吗"

### Q5 的猜测与回应

评审者猜"第 3 条（跳过必须显式）在其他领域会最先失效，因为业务上的跳过理由更多"。

**这个猜测部分成立，但失效方式与直觉相反。**

不是因为"业务理由多"——理由多恰恰更需要显式。真正先失效的是**第 4 条（跳过是分层的）**：

sdd-guard 处理的是**单一文档集合**，"整篇级跳过"只有一种（反引号未闭合）。
而迁移到 API 契约检查、数据质量校验时，被测对象是**分片**的
（每个 endpoint / 每张表 / 每个批次各自独立），于是：

> "这一条我跳过了" 与 "整个校验我跳过了" 会在同一个报告里混在一起，
> 而使用者默认读到的结论是后者。

**判据**：迁移到任何**分片对象**的领域时，必须先在报告结构上把
"条目级跳过"与"整体级跳过"分成两栏计数，否则第 4 条元判据会在无声中失效。

### 已经用真实证据验证过的迁移点

`--min-coverage` 的引入本身就是一次微型的跨领域迁移：
从"单条规则的四态"迁移到"整体覆盖率的四态"，立刻暴露出
"空集不构成通过"这条判据在**聚合层**同样适用（空 change 目录 ⇒ EXIT=0）。
